# The 3D digital reference vertical (#1015 Workstream 3)

`packages/backend/src/services/digital/profiles/` ·
`packages/backend/src/scripts/seed-digital-3d.ts` ·
`packages/shared-types/src/digital-3d-profile.ts`

> Binding: [ADR 0010](../adr/0010-digital-commerce.md), especially **D2** (what
> attaches where, and which configuration may be a variant) and **D12** (measured
> facts and seller claims are different TABLES). The domain it sits in:
> [digital-commerce.md](../digital-commerce.md). The machinery it is authored
> through: [product-types.md](../product-types.md),
> [catalog-cookbook.md](../catalog-cookbook.md).

One sentence: **the 3D metadata a buyer reads is a product type, not a React
component** — and the half of it Mercaria measured is not in the same place as the
half a seller claimed.

## What this package exists to prevent

The three #367 reference verticals each prevent one tempting modelling mistake.
This one prevents two, and they are the two that make a digital marketplace
unanswerable in a dispute:

| The mistake | What it costs |
|---|---|
| One place for "42,180 triangles" and "optimized for Unreal" | A product page that cannot say which facts Mercaria measured. The conformity basis ADR 0010 D11 replaces the goods guarantee with — *conformity with the DESCRIBED deliverable* — is then unanswerable, because nothing says what was described and what was measured |
| A variant per format, per licence, per engine | Twelve variants of one model, each with a price row, none of them a different thing. #1015 boundaries 5 and 6 |

## What it seeds

9 categories · 17 attribute definitions (36 controlled values) · **7 product
types** (96 fields across two flows) · 3 reference licences with version 1
published.

```
digital                                    (structural)
└── digital.three_d                         (structural)   3D models
    ├── …three_d.print_models               (selectable)   three_d_print_model
    ├── …three_d.game_assets                (selectable)   three_d_game_asset
    ├── …three_d.characters                 (selectable)   three_d_character
    ├── …three_d.environments               (selectable)   three_d_environment
    ├── …three_d.props                      (selectable)   three_d_prop
    ├── …three_d.archviz                    (selectable)   three_d_archviz_asset
    └── …three_d.materials_textures         (selectable)   three_d_material_texture_pack
```

**No brand, no canonical product, no variant, no asset, no store.** A reference
CATALOGUE of 3D models would be seven invented works with invented creator
credits, and a `digital_assets` row needs a `stores` row — so seeding one would
mint a fake creator account to own files that do not exist. What #1015 W3 asks for
is the PROFILES; the products are a creator's, and the journeys over them are
Phase C's.

### Why the keys say `three_d` and not `3d`

#1015 W3 names the profiles `3d_print_model`, `3d_game_asset` and so on, and a
leading digit is not a legal key: `PRODUCT_TYPE_KEY_PATTERN`,
`product_type_definitions_key_shape_check` and
`attribute_definitions_key_shape_check` all anchor on `^[a-z]`. So the epic's
spelling is the English and `three_d_*` is the key — the choice `DIGITAL_VERTICALS`
already made, its member being `three_d`. A test asserts the pattern REFUSES
`3d_print_model`, so the next reader does not conclude the profiles were renamed
for taste.

### Seven profiles and not one

A print model answers wall-thickness and support questions a material pack has no
meaning for; a character answers rig questions a prop does not. One
`three_d_model` type asking every question of everybody is the form nobody
finishes — and it would make "is this field relevant here" a renderer's guess
instead of a schema's answer. The field totals show it: a print model asks 14
merchant questions, a material pack asks 7, and a single type would have had to
ask all 17 of both.

## The provenance split, attribute by attribute

ADR 0010 D12 is the reason this workstream is not just "add some attributes". The
line is drawn at **what `asset_file_inspections` has a COLUMN for**, because that
is the only measurement a product page can render with a processor name and
version beside it. Every fact on the measured side is ABSENT from the seller's
vocabulary, so the two cannot disagree and nothing has to decide which copy is
true.

### Measured — `asset_file_inspections`, or a census over the package's files

| Fact | Where it comes from |
|---|---|
| polygon / triangle count | `triangle_count` |
| vertex count | `vertex_count` |
| separate mesh count — **and the number of printed PARTS** | `mesh_count` |
| dimensions (bounding box) | `bounding_box_{x,y,z}_mm`, all three or none by CHECK |
| **units** | the columns are named `_mm`; the inspector resolving a file authored in metres is what produced the number |
| watertight / manifold | `watertight` — NULL is *not determined* and is never *no* |
| UV mapped | `has_uv_mapping` |
| rigged | `has_rig` |
| animated, animation count | `animation_count` — *animated* is that count being positive, derived, never a second column |
| missing textures | `missing_resource_count` |
| the verdict, and the processor that produced it | `verdict`, `processor_name`, `processor_version` |
| formats included | `asset_files.format` over the package's members at one version |
| native / source format delivered | `asset_files` where `role = 'source'` |
| textures included | `asset_files` where `role = 'texture'` |
| **pre-sliced profile presence** | `asset_files` where `role = 'profile'` |
| file size | `sum(asset_files.byte_size)` over the package |

Two of those deserve the emphasis they have. **"Number of parts" is measured**,
because a part is a separate body and that is exactly what a mesh census counts.
**"Pre-sliced profile presence" is measured** because `ASSET_FILE_ROLES` already
has a `profile` member for that file — a checkbox beside it could disagree with
the contents of the download.

### Claimed — product-type attribute values, which is #367's machinery

*General (8).* `deliverable_configuration` (the one axis), `intended_use`,
`creator_credit`, `texture_resolution`, `pbr_workflow`, `lod_count`,
`engine_compatibility`, `software_version_compatibility`.

*Printable (9).* `print_process_suitability`, `minimum_wall_thickness`,
`support_requirement`, `presupported_files_included`, `print_in_place`,
`articulated`, `print_recommendation_notes`, `tested_printers`,
`tested_materials`.

The five that are claims for a REASON rather than by default:

- **`texture_resolution`** — a PNG's pixel dimensions are trivially measurable,
  but `ASSET_FORMAT_REGISTRY` marks `png` and `jpeg` `geometryMeasurable: false`
  and the inspection table has no dimension column. A "measured" 4K would be a
  number nobody produced.
- **`pbr_workflow`** — the inspector sees a texture file, not which slot a creator
  INTENDED it for. A roughness map and a glossiness map are the same bytes with
  opposite meanings.
- **`lod_count`** — an LOD chain is an authoring convention (`_LOD0`, `_LOD1`) the
  shipped inspector does not read. Answering it from `mesh_count` would report
  "4 LODs" for a four-part kit.
- **`presupported_files_included`** — support structures are geometry,
  indistinguishable from the model that needs them. Contrast the pre-sliced
  profile, which has its own file role and is therefore measured.
- **`print_process_suitability`** and the rest of the printable block — a
  JUDGEMENT. Suitability depends on wall thicknesses, overhangs and a material the
  platform never sees, and an analyzer answering it would be presenting an
  uncertain model as guaranteed printable.

### The claims a future measurement would make WRONG

`THREE_D_RETIRABLE_CLAIM_ATTRIBUTE_KEYS` names three —
`texture_resolution`, `minimum_wall_thickness`, `lod_count` — and it is not a
to-do list. Each is a fact no shipped processor reports, so a claim is the only
honest home for it today; what the list records is the DECISION that has to be
made when that changes. **A claim surviving beside a column measuring the same
thing is the disagreement D12 is about**, and the way that gets noticed is a
contradictory product page years later.

`three-d-profile-provenance.test.ts` holds the other half: every column the
registry names is resolved against the real drizzle table, and every column that
EXISTS must be classified — named by a measured fact, or exempted with a reason.
**A new measurement column fails the build until somebody classifies it**, which
forces the decision at the moment the column is added, by the person adding it.

## Variant axes: one, and why everything else is refused

`deliverable_configuration` is the only `variantDefining` attribute, and it is the
one ADR 0010 D2 names: `printable`, `game_ready`, `rigged`, `source_files`. It is
also the only `hardConstraintCapable` one, because a configuration is carried by
every variant that exists — so a shopper requiring `printable` excludes things
that genuinely are not, rather than excluding everything whose seller left a field
blank.

Three shapes are refused as axes, and **each by a different mechanism**, which is
what makes the refusal real rather than a convention:

| Tempting axis | What refuses it |
|---|---|
| A file format | There is no format attribute at all — the formats in the box are MEASURED. #1015 boundary 6: several formats belong to ONE purchased package, and an axis would make a buyer choose bytes |
| A licence tier | There is no licence attribute either. #1015 boundary 5: Personal €6 and Commercial €25 are two variants each BOUND to a licence option, and the rights live on a frozen licence version. A `licence_tier` enum would be a second, unversioned, unsnapshotted record of the terms |
| An engine, a printer, a material | `scope: 'compatibility'`, so `product_type_fields_variant_axis_check`'s FIRST conjunct refuses `variant_capable` on it whatever it is called — the brake-pad wall, one domain over |
| Everything else | `variantDefining` defaults FALSE, so `mercaria_native_variant_axis_citation` refuses a listing axis citing it |

**`PRODUCT_TYPE_FORBIDDEN_VARIANT_AXIS_KEYS` protects none of this, and that is
worth stating rather than discovering.** Its half of the CHECK is an EXACT-MATCH
list, and under a namespaced run the stored key is `run4a2b_tested_printers`,
which matches no entry however the list grows. The walls that actually hold here
are the scope conjunct and the citation trigger. A test asserts both halves — that
no 3D claim key is in the forbidden list, AND that a namespaced forbidden key is
not either — so the next reader does not mistake one wall for the other.

**`tested_printers` is free text at `compatibility` scope, and both halves are
deliberate.** `automotive_fitments` is what a Mercaria-RESOLVED compatibility
claim looks like: a verification state, narrowest-scope-wins, and an `unresolved`
answer for an ambiguous target. Routing one seller's successful print through that
machinery would publish their anecdote as a platform verdict for every owner of
that printer — which is exactly what #1015 W3's *"as claims, not global truth"*
forbids. Free text also keeps it out of the facet rail: an unbounded string facet
is a filter that does not work, the `footwear_colorway` ruling.

## The printable block is a VISIBILITY RULE, not a separate profile

A character can be printed, rigged for a game, or both. So the printable fields
are declared on the profiles where printing is a real route — print model,
character, prop — and guarded by one rule:

```ts
{ node: 'membership', field: 'intended_use', op: 'includes_any',
  values: ['physical_printing'] }
```

`includes_any` and not `eq`, because `intended_use` is a SET: a figurine sold for
printing AND for a game answers both, and an equality test against a multi-value
answer hides the block for exactly the seller with the most to say.

The alternative — `three_d_character_printable` and `three_d_character_game` —
would split ONE product into two classifications, so a search for characters would
have to know both and a creator selling the same figurine for both uses would have
to pick one or list twice. That is the variant explosion again, one level up.

Two mechanical consequences, both load-bearing:

- **`intended_use` is declared in EVERY flow that reads the guard.**
  `publishProductTypeVersion` refuses a version whose rule names a field the same
  FLOW does not declare (`visibility_rule_names_unknown_field`), because a
  merchant-only guard over a P2P field leaves that field hidden forever with every
  surface reporting success.
- **A guarded field is never `required`.** A `required` field behind a rule is
  required only while the rule stands; `recommended` survives the edit that
  removes the guard, and `required` would turn it into a wall for every seller who
  did not tick "for printing".

## The P2P flow is real here, and shorter

A studio publishing a game-asset pack and somebody uploading a model they made at
the weekend fill in the same profile. Every profile declares a `p2p` flow with two
or three questions — what it is, what it is for, and (if they said printing)
whether it needs supports — and nothing else. Demanding the studio's seventeen
fields of the second is how a marketplace loses its long tail, which is the whole
reason #367's flow vocabulary exists.

`scope`, `variant_capable` and `value_policy` are identical across the flows of one
attribute, because `mercaria_product_type_field_citation` refuses two flows
disagreeing about any of the three — who is asked varies per flow, what the
attribute IS does not.

## The reference licences, and the seeding path

`MERCARIA_REFERENCE_LICENCES` was data in `@mercaria/shared-types` that **nothing
wrote to a database**. A creator picking "the platform's standard commercial terms"
had nothing to point at, so #1015 acceptance criterion 2 was satisfiable only by
every creator drafting legal text.

`services/digital/profiles/licences.ts` writes them: an `asset_licences` row with
`authorship: 'mercaria_reference'` and `store_id NULL`, plus version 1 of its
terms, published. Three of each.

| Licence | Rights | Suggested update policy |
|---|---|---|
| `mercaria-personal` | personal use, modification | `purchased_version_only` |
| `mercaria-commercial-project` | + commercial project use, derivative redistribution | `same_major_version` |
| `mercaria-commercial-print` | + commercial physical production | `all_future_versions` |

The policies are **not uniform, and the asymmetry is the interesting part**. A
print licence buys a SHAPE, and a creator's v2 fixing a wall thickness is the same
shape. A commercial project licence is embedded in somebody's shipped game, where
a surprise v2 with different topology is a problem rather than a gift. A personal
licence at the cheapest price gets what was bought. **None of this is enforced by
the seed**: an `asset_licence_options` row names an asset and a package, the seed
creates neither, and binding a policy to an offer is a creator's act. The table is
the reference set answering the question once instead of seven creators guessing.

`source_redistribution` appears in none of the three, which is #1015 W2
requirement 6 holding by construction rather than by a flag nobody set — asserted
by a test.

### How it converges, and what "twice" means

Three distinguishable states a second run can meet, and the third is the one a
naive implementation gets wrong:

1. **Nothing there** — insert, publish.
2. **Version 1 PUBLISHED** — compare the stored terms against the published tuple
   and report `present` or `divergent`. Never correct: the terms are frozen by
   `asset_licence_versions_immutable_once_published`, so the only available
   correction is a raise from the database.
3. **Version 1 still `draft`** — what a run interrupted between the insert and the
   publish leaves. `findPublishedLicenceVersion` answers NULL for it, so a seed
   reading only that would insert version 1 again and die on
   `asset_licence_versions_licence_version_key` forever. This module reads the
   version by `(licence, version)` REGARDLESS of state and publishes the draft it
   finds.

That third state **cannot be manufactured in a test from a published row** — the
immutability trigger freezes `published_at` itself — so the decision is a pure
function, `decideLicenceVersionStep`, and `three-d-profiles.test.ts` drives all
four of its answers directly. That is the only arrangement in which the draft case
has a control at all.

**No feature lever gates the licence seed.** A licence row sells nothing, grants
nothing and authorizes no download; ADR 0010 D13's five levers gate uploads,
publication, paid checkout, downloads and a vertical; and D15 requires the tax,
provider and consumer-law sign-offs BEFORE `DIGITAL_PAID_CHECKOUT_ENABLED` goes on
for a market. A seed that refused to run until that flag was on would make
preparing the licence catalogue impossible until after the thing it is a
prerequisite for.

## Running it

```bash
# Dry run — the DEFAULT, and it reads the database.
bun run seed:digital-3d
bun run seed:digital-3d --licences-only

# Write.
bun run seed:digital-3d --apply
bun run seed:digital-3d --apply --namespace=demo
```

The root shortcut is `seed:digital-3d`, beside `seed:verticals`. The direct form
(`bun --cwd packages/backend src/scripts/seed-digital-3d.ts …`) is equivalent and
is what the shortcut runs.

Exit `0` means every declared row is present and agrees; `1` means the declared
expectation disagrees with the package data, or a step diverged, or the census
found the wrong number of rows, or it found none.

**There is no root `bun run` shortcut**, unlike `seed:verticals`. Adding
`"seed:digital-3d"` to the root `package.json` is a one-line change this
workstream does not own; until somebody makes it, the invocations above are the
whole interface.

### `--namespace` is for tests, and production wants it ABSENT

This is the one place the package's machinery deliberately DIFFERS from #367 W14's.
A vertical package always prefixes its keys, because `footwear` and `smartphone`
share one global key space. Here the product-type keys are PUBLISHED in
`@mercaria/shared-types`, so a production row keyed
`three_d_three_d_print_model` would make `THREE_D_PROFILE_KEYS` a list that
matches nothing in the database — and a key is frozen by trigger with no rename
available (ADR 0007 D1). So no `--namespace` means the canonical keys, and a
namespace means every key and slug is prefixed, which is what parallel test files
need against one shared database.

**The licences are never namespaced.** There is exactly one `mercaria-personal` in
the database, by a partial unique index over a NULL `store_id`, and that is the
point of a reference licence. A test run therefore shares those three rows with
every other run, and every licence assertion is an equality against the published
tuple rather than a count of what one run wrote.

### The measurement discipline

`census.ts`, and it is `scripts/seed-verticals/census.ts`' three layers:

1. **The vacuity floor.** `total === 0` answers `vacuous` BEFORE any comparison —
   seven zeros compared against seven zeros is `0 === 0` seven times, which every
   per-entity equality accepts. A distinct verdict from `mismatched`, because
   "nothing ran" and "one table is short" lead an operator to opposite actions.
2. **Equality, never a floor.** The tests assert the HIGH direction too.
3. **A positive control per entity kind** — and here ALL SEVEN are controls, which
   is the one place this census is stricter than the one it is modelled on: unlike
   a vehicle in a footwear package, there is no kind a real 3D package may declare
   none of.

The declared `expect` is written BY HAND and `deriveExpectation` recomputes it from
the package data; the CLI refuses to run if they disagree. A declaration spelled
`ATTRIBUTES.length` would agree with the derivation by construction, for any
package, including a broken one.

Counting is by the keys the package DECLARES, not by a `like` prefix: under the
canonical namespace the prefix is the empty string, so `like '%'` would count every
category in the database — a census that passes for a reason that has nothing to do
with this package.

### What the published module may never grow

`THREE_D_FORBIDDEN_PROFILE_SHAPES` names seven property names no shape in
`digital-3d-profile.ts` may declare — `requirement`, `flow`, `groupKey`,
`position`, `label`, `helpText`, `visibilityRule` — because every one is a property
of a FORM rather than of a vocabulary. A client holding `requirement` has the
authoring rule; holding `flow` has the audience; holding `groupKey` or `position`
has the layout; holding `label` has untranslated copy; holding `visibilityRule` has
the form's branching. All of them reach a client as an `AuthoringSchema` composed
per locale, per market and per flow — which is #1015 acceptance criterion 18 — and
a static copy in a published package is the hard-coded product form this epic is
arranged against. A test scans the module's own source for them, and drives the
detector against a mutated copy so it is shown to notice.

## What this package deliberately does NOT prove

- **That a buyer can buy one.** There is no store, no asset, no package, no offer
  and no listing here, so no download is authorized and no order exists. The
  purchase walk is `db/digital/__tests__/digital-commerce.realdb.test.ts`'.
- **That the measured side MEASURES anything.** The inspection pipeline is Phase
  B's; what this package holds is the line between the two provenances and a gate
  that fails when a new column crosses it.
- **That the 3D viewer renders any of it.** Phase C's, and the reason the
  published module carries keys rather than copy.
